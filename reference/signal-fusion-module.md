# JobMux — Signal-Fusion Module (Reference Implementation)

**Companion to `design/concept.md`, `design/architecture.md`, and `reference/adaptive-module.md`.** This file instantiates the evidence-gathering module named in `design/architecture.md` §1.2 as the **signal-fusion module** — the mechanism `design/concept.md` §4.1's case 4 describes, and the one the JobMux name itself refers to (`design/concept.md` §5). It does not restate what the module is for; `design/architecture.md` §1.2's own paragraph and §1.3's extension of "a signal is not a finding" to analog leads already do that. It is scoped narrowly: this file covers only the fusion mechanism itself — holding evidence as an open, tagged set of signals (`design/architecture.md` §1.4) and reconciling them into one confidence-rated status. It does not cover discovery of employers or listings in the first place (`reference/adaptive-module.md`'s job) or the board-heuristic/board-ML sweep (separate reference implementations not yet written).

**Validation status, stated plainly, updated after this module's first real pilot (2026-07-23).** The digital-side failure mode this module exists to catch — a listing that keeps rendering normally, with no visible expiration indicator, well past the point it stopped being real — is real and has been repeatedly confirmed in actual search work, most recently by this pilot's own direct re-check. The pilot also, for the first time, identified and drafted a real analog contact for a real ambiguous listing — but stopped there: per `design/architecture.md` §1.2's no-irreversible-actions rule, the system doesn't execute the outreach itself, so the loop isn't closed yet. The **Analog-pending** outcome added to §3 is a direct product of running this for real rather than only in the abstract: the gap between "digital confirmed, analog identified" and "analog actually resolves it" turned out to need its own status, not just a faster write-up of the existing ones. Full reconciliation across two independently-obtained real signals — the thing this file is actually about — still hasn't happened; that remains the next validation step once a real analog response exists. Treat this file's worked walkthrough (§6) accordingly — it is explicitly invented, not a case history, and remains so even after this pilot.

As with the two companion files: this file states the current template as decided. When it changes, rewrite the relevant section in place.

## 0. When this module runs

This module triggers on a specific, narrower condition than "a listing exists" or "a listing looks stale." It triggers when a **digital trace is a weak or misleading proxy for real availability** — not merely absent (that's a discovery problem, `reference/adaptive-module.md`'s domain) but *present and actively misleading if taken at face value*. Two shapes of this have been identified so far, and this module treats them differently because they fail in different directions:

- **Stale-but-rendering.** A listing page loads cleanly, reads like a live posting, and shows no visible "expired" or "closed" indicator — but a date field on the page (a closing date, a posted date well past the sector's typical listing lifespan) shows it's actually past its real term. The digital trace here isn't silent; it's actively asserting "I'm current" through the mere fact that it loads, while a separate piece of data on the same page contradicts that assertion. The failure mode this module exists to prevent is trusting the page's *renderedness* over its *date field*.
- **Evergreen "always hiring."** A posting states, explicitly or in effect, that the employer is continuously accepting applications rather than filling one bounded opening. This isn't stale in the same sense — it may be entirely accurate as written — but it's low-information by design: it can't tell you whether there's a real, current opening worth a candidate's time today, only that the employer has left the door open in principle. Treating an evergreen posting as equivalent to a normal open listing overstates what it actually confirms.

Both shapes share the same consequence: the digital trace alone cannot responsibly resolve a status, and pursuing an independent analog lead (§2) is the only way to close the gap — not a second-choice fallback used only when the digital trace is completely unavailable. That's the trigger condition for this module specifically, as distinct from a simple "listing not found anywhere" case (discovery) or a listing that loads with unambiguous current information (no fusion needed — verify it directly per `design/architecture.md` §1.3's base rule and move on).

## 1. Core discipline: independent signals in an open set, not whichever arrived first

Once a digital trace has triggered this module, obtaining an analog lead does not resolve the situation by replacing the digital trace — it produces one more tagged entry in the same open evidence-signal set (`design/architecture.md` §1.4), not a correction that supersedes what's already there. The set is not capped at two: a board-heuristic-sourced signal and a board-ML-sourced signal about the same listing can both be present alongside an analog lead, and the same disciplines below apply regardless of how many signals are in play. Two disciplines follow directly from holding an open set rather than a single replaceable value:

- **No signal is presumptively senior.** A newly-obtained analog lead does not automatically outrank an older digital trace just because it was collected more recently in the researcher's own workflow, and a digital trace does not automatically outrank an analog lead just because it's the more familiar, more mechanical channel to check. Reconciliation (§3) weighs each signal on its own merits — how directly it speaks to the actual question, how recent the *underlying event* is (when the page last changed, when the analog contact actually knows the status as of), and how specific it is to this listing rather than the employer in general — never on which one happened to arrive first in the course of the search.
- **A disagreement within the set is itself a finding, not an error to average away.** If signals in the set point in different directions, that disagreement gets characterized as discordant and recorded as its own status (§3) rather than silently resolved by picking whichever signal the researcher trusts more by default. This is the direct extension of `design/architecture.md` §1.3's "a signal can motivate a check, it can never be the check" to a case with more than one signal: no single signal, alone, is the check. The check is holding the whole set and reasoning about what any disagreement within it actually means.

## 2. The analog side: how AnalogSearch supplies it here

AnalogSearch (`design/architecture.md` §1.2) is the same named technique `reference/adaptive-module.md` §3 uses for gatekeeper/network discovery — pursuing a human or relational channel rather than a digital query. The two uses differ in what they're trying to establish, which changes what "success" looks like:

- In `reference/adaptive-module.md` §3, AnalogSearch is used to identify and reach an authoritative *channel* — confirming which association or body is the real gatekeeper for a sector, and whether it runs a private distribution list. The object of inquiry is the channel itself.
- Here, AnalogSearch is used to obtain a lead about one *specific, already-identified listing* — direct contact asking, in effect, "is this particular posting still open, and if not, is anything like it coming back." The object of inquiry is a status, not a channel. The channel used to reach that status (a phone call to the department or employer named on the listing, a contact at an already-confirmed gatekeeper body, a direct question to a professional association's staff) may be one already established by a prior gatekeeper/network discovery pass — this module doesn't re-derive the channel from scratch if `reference/adaptive-module.md` §3 has already done that work for the same employer or sector — but it also doesn't presume a channel exists just because the digital trace triggered this module. Where no channel has been established yet, resolving that is itself gatekeeper/network discovery and follows §3 of the companion file, including its three-way wrong/defunct/unsafe trust check, before any analog contact is attempted.

**Escalation ladder, instantiated for this module's typical failure mode — a digital trace that's ambiguous or provably stale, with no analog lead obtained yet:**

1. Confirm or establish the right analog channel for this specific employer or listing (reuse an already-confirmed channel from `reference/adaptive-module.md` §3 where one exists; otherwise run that section's discovery and trust check first).
2. Make direct contact — a phone call, a direct message, an in-person inquiry where plausible — asking specifically about the listing in question, not a general "are you hiring" that wouldn't resolve the actual trigger condition (a stale date field, an evergreen posting's real current need).
3. If contact succeeds and yields a clear answer, that answer is the analog signal — held separately from the digital trace per §1, not yet treated as the final status until reconciliation (§3) runs.
4. If contact can't be reached, doesn't know, or won't confirm, record the analog side distinctly as unresolved rather than silently falling back to the digital trace as if the analog attempt had never been made — doing so would recreate exactly the failure this module exists to prevent, just one level removed.

## 3. Reconciliation into a confidence-rated status

Judging what state any one signal in the set deserves — a digital trace's reliability, an analog lead's recency and specificity, whether either has gone stale — is a frontier-tier task (`design/architecture.md` §2.3, §1.4): it requires judgment, not mechanical comparison, and is never delegated to a smaller model or resolved by a fixed rule (e.g., "analog always wins," "the newer signal wins") that would remove the judgment call the architecture doc explicitly reserves for this step.

Once every signal in the set already carries its own state, deriving an outcome label and a numeric confidence value from the set as a whole — characterizing it as concordant or discordant, then producing a label and a number from that characterization — is algorithmic (`design/architecture.md` §1.4, §2.3): mechanical, given the inputs, even though producing those inputs wasn't. This is also where this file's own confidence-label question, and the matching questions `reference/adaptive-module.md` §10 and `reference/verification-escalation-policy.md` §7 flagged, actually get resolved: the closed vocabulary lives in `design/architecture.md` §1.4 now, as one general model shared by every evidence-gathering module, not a fixed enumeration this file owns on its own.

The named outcomes below are this module's own catalog — the labels its typical two- or three-signal shapes (a digital trace plus an analog lead; occasionally a board-heuristic-sourced signal and a board-ML-sourced signal about the same listing, plus an analog lead) actually produce under that general rule. They're worked examples of the general model's output, not a separate closed enumeration of their own:

- **Concordant confirmation.** Every signal in the set agrees — typically a digital trace and an analog lead, but the same label applies with more signals present. This is the highest-confidence outcome this module can produce, precisely because it's the case where independent signals corroborate each other rather than one being trusted alone.
- **Analog-resolved.** The digital trace remained genuinely ambiguous or was confirmed stale (§0), and the analog lead is what actually resolves the status. Tagged distinctly from a concordant confirmation — it rests on one channel, not two agreeing — and distinctly from a plain `confirmed-analog` label elsewhere in the system, since here it specifically follows a digital trace that misled or fell short, which is worth preserving as context for anyone reviewing the row later.
- **Digital-only, capped confidence.** The analog channel couldn't be reached or wouldn't confirm (§2, step 4), and only the digital trace is available. Because this module exists precisely because digital traces of this shape (stale-but-rendering, evergreen) are weak proxies, this outcome is not treated as equivalent to a normal direct-load confirmation elsewhere in the system (`design/architecture.md` §1.3's base case) — it's recorded with the cap explicit, and the unresolved analog attempt is recorded alongside it rather than dropped.
- **Analog-pending.** Distinct from digital-only, and added after this module's first real pilot surfaced the gap: `design/architecture.md` §1.2's "no irreversible actions" rule means the system itself never sends the email or makes the call — AnalogSearch's actual execution is drafted and handed to the candidate, not carried out automatically. Between the digital trace being (re-)confirmed and the candidate actually executing the drafted outreach, the honest status is neither "digital-only" (which implies an analog attempt was made and failed) nor any of the other outcomes below — it's a fifth, transitional state: digital side confirmed, analog contact identified and drafted, execution pending a human. Recorded distinctly so it doesn't get silently treated as equivalent to a channel that was tried and came up empty.
- **Conflicting signals.** Digital trace and analog lead point in different directions after a genuine reconciliation attempt. This is not an error state to be resolved by silently picking a side — it is recorded as its own outcome, with both signals and the reasoning that failed to reconcile them preserved. Where the frontier-tier judgment call can responsibly break the tie (one signal is clearly more specific to this listing, clearly more recent in underlying-event terms, or the other channel has a known reliability problem already documented elsewhere, e.g. via `reference/adaptive-module.md` §3's trust check), it should, and the resolution and its reasoning are recorded together with the status. Where it can't, the status stays **Conflicting** rather than being forced.
- **Unable to verify.** Neither channel produced usable evidence after the escalation ladder (§2) was exhausted. Recorded distinctly, never folded into a confirmed-negative bucket — the same discipline `design/architecture.md` §1.3's own escalation ladder already requires for a single-channel dead end.

## 4. What this module does not do

Consistent with `design/architecture.md` §1.2's "evidence, not advice" discipline: this module reports a reconciled, confidence-rated status. It does not judge whether that status makes the listing a good fit for the candidate — that's the plan stage's job, downstream and later (`design/architecture.md` §1.4). A **Conflicting** or **Unable to verify** outcome is real information to hand forward, not a failure this module needs to resolve into a clean yes/no before reporting.

## 5. Recheck cadence

The standard volatility-tier and funding/cycle-aware scheduling (`design/architecture.md` §1.4, `reference/adaptive-module.md` §8) applies to rows this module has produced a status for, with no special mechanism beyond what those sections already specify for a **Concordant confirmation**, an **Analog-resolved** status, or a capped **Digital-only** status. Whether a **Conflicting**, **Unable to verify**, or (added after the first real pilot) **Analog-pending** outcome should default to a *shorter* recheck interval than the same row's ordinary volatility tier would otherwise assign — on the reasoning that an unresolved, contradictory, or execution-blocked status is itself a sign of a situation worth revisiting sooner — is not settled by anything in `design/architecture.md` today. **Analog-pending** specifically raises a variant of this question the other two don't: the right recheck trigger for it may not be time-based at all, but event-based — reprompt once the candidate confirms the drafted outreach was actually sent, rather than on any fixed calendar interval. Flagged in §7 rather than decided here.

## 6. Worked walkthrough (hypothetical, not a validated case)

The following is invented for illustration and marked as such throughout — it is not a report of anything actually run.

> Suppose a listing on a public-sector job-posting platform loads cleanly and reads like an open role, but its stated closing date is several months in the past with no "expired" banner anywhere on the page — the stale-but-rendering trigger (§0). A direct reload confirms the date field itself, not just the page's general appearance, per `design/architecture.md` §1.3's base rule: the page is real, current in the sense that it loads, but the date on it says otherwise.
>
> A channel to the hiring department was already established during an earlier gatekeeper/network discovery pass for this employer, so no new channel-discovery work is needed (§2). A call is placed asking specifically about this posting, not a general staffing question. Suppose the department confirms the role was filled shortly after the stated closing date and the listing simply hasn't been taken down — an **Analog-resolved** outcome, with the digital trace's misleading renderedness now explained rather than left ambiguous.
>
> Suppose instead a different listing, at a different employer, describes itself as continuously accepting applications rather than naming one bounded opening — the evergreen trigger (§0). Analog contact this time reaches someone willing to say only that "we're always interested in strong candidates," without confirming any current, specific need. That's a real analog attempt that didn't resolve anything more specific than the posting itself already said — recorded as **Digital-only, capped confidence**, with the unresolved analog attempt noted, rather than treated as a genuine confirmation either way.
>
> Suppose a third case: the digital trace on a listing looks current and well within its stated term, but an analog contact independently volunteers that the position was actually pulled internally last week and the posting is being left up while a formal close-out is processed. Here the two signals disagree outright. If nothing about either channel's reliability or specificity clearly favors one over the other, the honest status is **Conflicting** — recorded with both signals intact, not quietly resolved toward whichever one the researcher happened to check last.

## §7 — partially resolved

The confidence-label vocabulary this section used to reference as unresolved is now settled: `design/architecture.md` §1.4 defines the general evidence-signal model the outcome labels above are derived from (§3), replacing the earlier "working set... not a final decision" framing. What §7 actually asked, though, is narrower than that and remains open: whether a **Conflicting**, **Unable to verify**, or **Analog-pending** status should carry its own default recheck behavior, distinct from the row's ordinary volatility tier. Nothing in the current decision settles this — `design/architecture.md` §1.4 now gives every row a numeric confidence value (§3, above) that could plausibly inform a shorter recheck interval for these three outcomes, but whether it should, and by what rule, is a scheduling-layer (§1.5) question this decision didn't reach. **Analog-pending**'s event-based-trigger question specifically (reprompt once the candidate confirms the drafted outreach was sent, and again once a response arrives) is even more clearly untouched by anything decided so far. Both remain flagged, not decided.
