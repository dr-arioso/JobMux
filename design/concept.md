# JobMux — Concept Brief

**Purpose of this file.** This is the entry point for a new session working on JobMux — a reusable, open-source-able Claude Skill for structured job searching. This file states the current design as decided. It does not narrate how the design got here — no "an earlier draft assumed X, a later session corrected it." When a decision changes, rewrite the relevant section in place; don't append a dated correction on top of it. Alternatives that were seriously considered and rejected are kept, but as standing reasoning in their own "alternatives considered" material — stated flatly, not as a story about when they were rejected. Read this whole file before doing anything else. It intentionally does not carry over the personal details of the real search that motivated this project — treat this as a design brief, not a transcript.

**Companion file:** `design/architecture.md` holds the actual system design — the four reusable layers and the format/infrastructure options. Read this file first for the why and the landscape; read the architecture doc next for the how.

## 1. Background

The project is a three-stage pipeline, built as three separated systems rather than one blended assistant:

1. An adaptive, gated interview that resolves a small number of candidate-specific decision nodes — one question at a time, forbidden from making market claims or recommendations while interviewing, gated so the plan cannot be written until each decision node is resolved in the candidate's own words (or explicitly, honestly left open, carried forward with a conditional recommendation per branch).
2. An evidence-only search stage, run separately, with a hard precondition (real web access, or it must refuse rather than guess), forbidden from inventing employers or listings, forbidden from scoring or ranking fit, and required to report "none found" as real information.
3. A plan that recombines the two — the interview's resolved decision nodes and ranked priorities against the search's evidence — to make the actual fit judgments, branch the strategy, and hand back a concrete timeline.

The decision nodes that came out of the original source search (a binding geographic constraint, how a job's career phase should count in scoring, a move-timing question) are one candidate's answers, not inputs the system is built around. **Generalizing this correctly means describing the method for finding a given candidate's decision nodes, not shipping a fixed list as if it's universal.**

The pipeline loops rather than running once: recombination re-runs every time the elicitation layer's live state changes (architecture doc §1.1), not just once at a linear handoff.

## 2. Landscape — what already exists

Several open-source AI-driven job search tools exist, mostly built as Claude Code skills or CLI agents:

- **ai-job-search** (MadsLorentzen) — evaluates postings, tailors CVs, writes cover letters, ATS-keyword checks, LaTeX PDF generation.
- **career-ops** (santifer) — scans 45–150+ company career pages via Playwright, scores listings 1.0–5.0 against a resume via a five-dimension rubric, generates ATS-optimized resumes, drafts answers on Greenhouse/Ashby/Lever forms, tracks a pipeline. Requires the company list to be pre-configured during setup — it evaluates and ranks against employers already named, not employers the user doesn't know exist yet.
- **AIHawk** / **autopilot-jobhunt** — scrapes LinkedIn, Indeed, StepStone (RemoteOK in some forks) directly and auto-applies. A pure aggregator-scraper, with no known-employer/discovery distinction and no reversibility discipline (see architecture doc §1.2 on irreversible actions). AIHawk's original repository was archived in mid-2026 and is no longer actively maintained by its original author; it survives only as community forks — worth keeping current here rather than citing it as if it were a live, maintained project.
- **Proficiently Claude Skills** — resume tailoring, cover letters, a LinkedIn-contacts-to-company-openings scan.
- **JobSpy** (speedyapply) — a pip-installable Python library, not a Claude Skill or agent: scrapes LinkedIn, Indeed, Glassdoor, Google Jobs, ZipRecruiter, and others concurrently into one dataframe. No evaluation, interview, or discovery layer at all — a pure scraping dependency, and a candidate piece of literal reusable code for this project's own broad ATS/job-board module (architecture doc §1.2, §1.5).
- **freehire** (strelov1) — a self-hostable, MIT-licensed job aggregator that crawls company ATS pages directly (Workday, Greenhouse, iCIMS, Ashby, Lever, and a long tail of others) into one normalized, deduplicated schema, with a pluggable per-platform source-adapter registry. Scoped to IT/tech roles specifically, so not a usable data source for a search outside tech — but a clean, real reference implementation of the fetch → normalize → dedup → upsert pipeline shape this project's own broad ATS module needs, worth studying rather than reusing directly.
- **jobseek** (colophon-group) — monitors 4,400+ company career pages directly rather than aggregating from job boards; MIT-licensed code, CC BY-NC-licensed job data. Same tech/adjacent-sector scope limit as freehire. Notable for an onboarding workflow built to be run by a coding agent rather than a human: a CLI tool that walks an agent through finding a requested company's career page, picking the right monitor/scraper, and opening a PR — a pattern worth borrowing for this project's own fragmented-small-employer module once it moves from design to implementation.
- **JobSync** (Gsync) — a self-hosted application tracker with AI resume review and AI job-match scoring, architecturally distinct from the scanning/discovery tools above. Like career-ops and ai-job-search, its ground is application tracking and document work, not discovery — another confirmation of where this project's boundary sits (§3).

None of these separate "figure out what actually matters to this person" from "find evidence" from "judge fit" into distinct, gated stages. The real gap isn't aggregator-vs-not; it's **known-employer evaluation vs. employer discovery in a fragmented, small-employer market.** career-ops is strong at the former; nothing found does the latter as a first-class, separately-gated stage.

## 3. The differentiated problem

The generalizable claim is **not** "this is for candidates with a hard geographic anchor." It's: most people don't actually know which 2–4 things genuinely decide their own job search until someone interviews them well; most job-search tools skip past that question straight to matching against a resume; and conflating discovery with fit-judgment produces worse plans than keeping them separate. A geographic anchor was one candidate's answer — someone else's decision nodes might be a compensation floor, a values/mission-alignment requirement, a caregiving-driven schedule constraint, a visa/credentialing barrier, or a career-pivot question about which skills transfer.

**JobMux doesn't compete on document generation, application pipelines, or interview preparation.** Existing tools already do resume tailoring, cover-letter drafting, ATS-form autofill, and — confirmed directly in both career-ops's and ai-job-search's actual code — a full interview-prep story bank, complete with tagged, retrievable past answers for reuse across a search. JobMux isn't trying to replace any of that layer, and currently lacks it entirely; that's likely permanent rather than a gap to close later. The claim is narrower and complementary: a deeper, more customizable, more exploratory and adaptive search *strategy* — the part upstream of "now that I have a shortlist, help me apply." Not an attempt to corner the whole job-search market, just the part of it existing tools handle worst.

The honest answer to "why use JobMux instead of career-ops (or ai-job-search, or AIHawk)" is that the question is the wrong shape. Those are all-in-one job search, resume, and search-through-interview suites, and they're good at that whole pipeline. JobMux gathers job information from the big aggregators the same way they do, then synthesizes it against signals those tools aren't built to look for — surfacing new results, measuring posting freshness and fit, and excavating concrete networking contacts for openings that may not be found anywhere on the internet. Use each for what it's for.

**Not every candidate needs the heavy machinery.** The interview and the dynamic prioritization/cost-aware search apparatus (architecture doc §1.5) are worth their overhead for a candidate whose market is genuinely fragmented and whose decision nodes are genuinely decisive — plenty of real searches are neither. The system includes an explicit triage step up front: does this situation look complex/fragmented enough to warrant the full elicitation and modular discovery apparatus, or would a lighter existing tool (career-ops) serve this candidate just as well. Case 3 below is the test of that triage step.

## 4. Use cases

### 4.1 Active proof-of-concept set

Chosen to vary which decision node or priority is decisive, and which capability each one proves — not just to vary industry or geography.

**Case 1 — geographic anchor + fragmented small-employer market (environmental science, Mankato MN).** The validated baseline: a candidate whose dominant decision node is a hard geographic anchor into a sector with small, scattered employers. Exercises the fragmented-small-employer discovery module and the verification layer hardest, and is where the concrete existing-tool misses live — a Watonwan County SWCD opening invisible to a normal Indeed search, an Olmsted County "Health and Safety Specialist – Solid Waste" posting cross-titled past any keyword sweep, MASWCD's private weekly email loop that no crawler reaches. This case doesn't need new work to re-prove; it's the calibration case the others are measured against.

**Case 2 — values/mission-alignment decision node.** A candidate whose dominant decision node is "only wants to work for organizations meeting some ethical bar." Exercises a genuinely different evidence-gathering module — employer research against stated values, not listing discovery — and different verification demands (judging whether an org's public claims hold up, not whether a listing is live). This is the case that answers "does this only work for one shape of problem": it's the decision node furthest in kind from geography.

**Case 3 — thick market, simple priorities (foil).** A candidate whose dominant decision node is closer to "open to relocation, needs a compensation floor met, industry-agnostic," in a well-aggregated market. The full elicitation-plus-triage step should run and correctly conclude that the heavy machinery isn't warranted here — that broad ATS scanning (what career-ops already does well) is the better tool. This is the case that makes "worth building" a credible claim rather than a blanket one: a tool that claims to beat existing options everywhere, with no acknowledged limit, isn't believable.

**Case 4 — analog/digital signal fusion (primary current creative focus).** A market where a digital trace exists but is a weak or misleading proxy for real availability, and an analog channel is what actually resolves it. Two concrete shapes, both already observed rather than hypothetical: a GovernmentJobs.com listing that keeps rendering normally for months after its real closing date (architecture doc §1.3) — the digital trace looks live but isn't, and a call to the department is what tells you whether it's genuinely closed or about to repost; and an evergreen "always accepting applications" nonprofit or small-firm posting — low-signal on its own — where the real current need only surfaces by asking someone directly. Neither channel alone is trustworthy here; the tool holds the digital trace as one signal and the analog lead as another, and reconciles them into a single confidence-rated answer instead of treating whichever arrived first as the finding. This extends the verification layer's "a signal, not a finding" rule to analog leads for the first time, not just search-tool output, and it's the mechanism the JobMux name refers to (§5). The technique behind gathering that analog lead in the first place — AnalogSearch — is also what powers gatekeeper/network discovery (architecture doc §1.2): the same act of pursuing a human channel rather than a digital one, whether the goal is verifying a stale listing or discovering an opening with no digital footprint at all.

### 4.2 Roadmap — deferred, analog-only cases

Markets with no digital trace at all to fuse against — valuable once the fusion mechanism (case 4) is proven, not before:

- **Union hiring hall / JATC apprenticeship intake** (electricians, plumbers, ironworkers, pipefitters). No conventional listings; openings surface as periodic intake windows announced via a newsletter, a notice at the hall, or word of mouth. The dominant decision node is jurisdiction (which local covers a given location) plus a career-pivot/credentialing question, not commute-radius geography. Existing tools have nothing to offer here at all, since there's nothing to scrape or evaluate — the strongest possible test of gatekeeper/network discovery (architecture doc §1.2) and funding/cycle-aware recheck cadence (§1.4).
- **Tribal enterprise/government hiring** — similar relational-channel shape, usually paired with a cultural-affinity anchor.
- **Faith-based "call process" placement offices** (denominational HR — ELCA, Catholic diocese, UMC) — genuinely analog, a smaller and more idiosyncratic market to validate against.

### 4.3 Sector/domain backlog (unconfirmed hypotheses)

Candidates for testing whether the fragmented-small-employer module (case 1's module) generalizes to other sectors. **The heuristic: field size doesn't predict whether a search needs this treatment — field structure does.** Nursing and accounting are huge fields well-served by mainstream aggregators because their typical employers are large multi-site institutions with mature ATS pipelines. Environmental science's problem is that its typical employers skew toward small, independently-run organizations that either lack real ATS infrastructure or rely on a professional association's private distribution channel instead of a public board. The test for a candidate field: do its typical employers run their own small-scale, uncentralized hiring process, and is there a professional association plausibly serving as an informal distribution layer a general search wouldn't see?

Sector-level candidates: hyper-local government (townships, small municipal utilities, joint-powers boards, county extension offices), museums/archives/small cultural institutions, non-teaching K-12 roles, rural/critical-access healthcare support, veterinary and animal welfare (rural), local journalism and community media.

Degree/training-domain candidates: forestry, hydrogeology, agronomy/soil science, wildlife biology (share literal employers with environmental science); urban/regional planning and emergency management at hyper-local scale; social work and public health with a rural/tribal concentration; library science and museum studies/public history/archives; special-education cooperative roles (rural speech-language pathology, school psychology); cooperative extension roles (4-H, ag extension educators).

These are unconfirmed hypotheses, not chosen cases — before picking one for a real build, it needs the same structural verification the SWCD sweep did for environmental science (does this field's employer base actually lack ATS infrastructure, does a private/association channel actually exist), not an assumption that the pattern transfers because it sounds plausible. Note: urban/regional planning and library science are additional structural mirrors to case 1 (fragmented small employers, a different professional-association dynamic) — useful for validating case 1's module against a second sector later, not a substitute for a genuinely different-decision-node case like 2 or 3.

## 5. Name: JobMux

Decided. The name refers to the mechanism, not just the problem: a multiplexer takes multiple heterogeneous input signals and combines them into one coherent output — exactly what case 4's fusion capability does with a stale digital posting and an analog tip. It reflects the broader ethos this project shares with StashKit: taking messy, partial, sometimes-contradictory real-world input and turning it into one salient, trustworthy signal.

**Alternatives considered:** *Long-Tail Jobs* (borrows the recommendation-systems/retail term for low-volume niches outside a mainstream ranking's "hits" — credible, but names the market shape, not the mechanism), *Unlisted Jobs* / *Off-Book Jobs* / *The Grapevine Market* (name the private-channel problem specifically, not the fusion capability that's now the primary focus), *Off the Beaten Job Track* (this project folder's existing name, chosen on instinct before any naming discussion — fine as a folder name, superseded by JobMux as the project's actual name). JobMux wins because it's mechanism-first and covers the current primary case (fusion), rather than only the private-channel problem, which is now one of several things the design handles.

## 6. Bootstrapping instructions for a new session

1. Read this file and `design/architecture.md` in full first.
2. If given access to the source project's folder, the highest-value files are the interview system prompt, the search-framework template, and the values-phase addendum (filenames evident from that folder's own index) — these hold the real elicitation and template-instantiation mechanics in more operational detail than these two files reproduce. Treat tracking/methodology files (ledger schema, re-check methodology notes) as secondary material for architecture doc §1.3–§1.4.
3. Mine all of it for patterns, not verbatim content. Several parts of the source project are specific to one candidate's real personal situation (name, location, employer contact names/emails) and must not end up in anything meant for open-source release. When in doubt, generalize the pattern and drop the specific.
4. The four active use cases (§4.1) are decided; confirm before drafting anything if circumstances have changed since this was written.
5. Suggested build order: (a) the elicitation layer — a method for discovering a candidate's decision nodes (not a fixed list) plus the values pairwise-ranking mechanism; (b) the evidence-gathering layer as pluggable modules, with the fragmented-small-employer module (case 1) and the signal-fusion capability (case 4) both written up in full as reference implementations; (c) the verification/escalation rules as a standing, template-instantiated policy doc; (d) the recombination/tracking schema and disposition taxonomy as a template; (e) assemble everything into SKILL.md; (f) sanity-check that the reference docs would still make sense pulled into a plain repo with no Claude-specific framing.
6. Before publishing anything, do one explicit pass checking for any leaked personal/identifying detail from the source project.
7. Before building the discovery module's aggregator/ATS-facing rung (architecture doc §1.5), study career-ops's and AIHawk's actual open-source implementations (URL/pattern detection for Greenhouse/Ashby/Lever, career-ops's Playwright navigation approach and evaluation rubric) rather than re-deriving that layer from scratch. Before writing any state to disk, settle on the thin storage interface (architecture doc §2.4) first, even if the backend underneath starts as plain files.
