# JobMux — Architecture

**Companion to `design/concept.md`.** That file holds the background, the differentiated-problem framing, the use cases, and the naming decision. This file holds the system design: the reusable layers, and the format/infrastructure options. This file states the current design as decided — it does not narrate how it got here. When a decision changes, rewrite the relevant section in place rather than appending a dated correction. Alternatives seriously considered and rejected are kept as standing reasoning, not as a story about when they were rejected.

## 1. Reusable layers

### 1.1 Elicitation layer (the center of gravity)

Not a preliminary questionnaire — the piece that determines what the other layers need to do. Two components:

**The interview.** One question per turn, following the candidate's thread rather than running a checklist. The interviewer holds working hypotheses about what the candidate's decision nodes might be, stated up front and explicitly revisable, tested against what the candidate actually says — confirmation counts, "the brief said so" does not. A decision node can be legitimately resolved as genuinely open, carried into the plan with a conditional recommendation per branch — that's a valid finding, not a failure to interview hard enough. A decision node may have child decision nodes, unlocked only once a parent resolves in a way that makes them relevant (a geographic decision node resolving "yes, this matters" is what makes "a hard boundary or a gradated radius" worth asking at all; if it resolves "no," the child question never comes up). The interview is barred from making local-market claims or recommendations while it's still asking questions (no employer names, no "there's probably demand for X here") — that discipline keeps discovery a separate, later, evidence-gathering step. The method generalizes; a fixed list of decision nodes (location / move-timing / career phase) does not — those were one candidate's answers.

**Values pass.** A short, bounded step that produces the candidate's priorities, organized into dimensions, plus the structured attribute vocabulary the evidence-gathering layer needs to score against them.

A **priority** is a single value scored against listings. Offer a small starter set (variety, scheduling flexibility, commute tolerance, compensation, solo-vs-team, structure-vs-autonomy, growth — adjust per domain), let the candidate add or rename. Every priority has a *shape*: **target** (a specific point or identity value — desired location, desired occupation, desired industry — where fit is proximity or match to that point, not "more is better"), **scalar** (an absolute, ordered axis where more or less is monotonically better, usually with a floor and/or ceiling of diminishing returns — salary, PTO days, commute distance), or **polarity** (a bipolar spectrum between two named, roughly-opposite qualities — autonomy vs. structure, variety vs. consistency — where fit is alignment between the candidate's stated lean and a listing's inferred position on the same line). Shape is determined by how the candidate actually talks about a given priority, not assigned from a fixed lookup keyed on its name — the same "confirmation counts" discipline as the interview.

A priority may independently carry a **threshold** (a cutoff on an existing continuous scale — applies naturally to scalars and polarities) and/or, for a target specifically, be marked **mandatory** (a boolean — a target has no natural continuum to hang a graded cutoff on the way a scalar does; the candidate-facing term for this flag is **non-negotiable**). Either mechanism can make a priority **controlling** for a given listing — a per-(priority, listing) evaluation outcome, computed fresh each time, never a fixed property of the priority itself. A priority is controlling for a listing when its threshold is unmet or its mandatory target isn't matched, in which case it dominates and the listing is effectively excluded regardless of how well it scores elsewhere. It's **non-controlling** when the threshold is cleared (or none is set), or the target isn't mandatory (or is matched) — in which case the priority behaves normally, contributing its rank to the overall score if it has one. The same priority can be controlling for one listing and non-controlling for another. (This pattern — a hard, non-negotiable stop independent of an otherwise-scored dimension — isn't unique to this design; ai-job-search's own evaluation framework models location the same way, a literal pass/fail dimension with "requires relocation" marked as a deal-breaker.)

A priority may also carry a **rank** — a cardinal weight produced by a pairwise forced-choice tournament within its dimension, converted from win-rates via a Bradley-Terry-style model rather than just read off the final order (this retains information the tournament already generates; no separate elicitation step is needed). The tournament runs until a stable top two or three holds — a full sort of the tail isn't forced. Priorities are grouped into named **dimensions** (see below).

**Category filter.** Not every candidate preference is target/scalar/polarity-shaped. Some are a fixed, named set of discrete labels, where the candidate maintains a currently-**acceptable subset** (a filter, structurally parallel to a threshold, but over a discrete set rather than a continuous scale) and **ranks** the accepted labels by current desirability — both live, mutable state. Career phase (below) is one instance of this shape. **Employment type** is another — full time, part time, contractor, temporary, intern, volunteer, per diem — and its label set doesn't need to be invented: it's adopted directly from schema.org's `JobPosting.employmentType` enum, written in plain form in this document but using the exact token when implementing structured-data extraction. **Work schedule** (day shift, second shift, overnight, rotating, flexible/exempt) is a third instance, with no equivalent existing standard — this is a case where JobMux does need to define its own vocabulary rather than adopt one. Occupation and industry (below) can also take this shape instead of being a single target, when a candidate is open to more than one, ranked.

**Career phase.** A named, ordinal set of stops describing what role a given opportunity plays in the candidate's career trajectory right now — for instance, purely a paycheck, an enjoyable detour unrelated to any career build, a role that builds toward the candidate's career without being the ideal fit, or a role that's a strong direct fit. As with the decision-node list and the dimension set, the exact stops are a per-candidate instantiation of the method, not a fixed universal scale — the pattern doesn't presume every candidate has a single target occupation to measure relevance against. Whether career phase matters at all, and how finely it should be staged, is itself resolved by a decision node. Career phase is a category filter: the candidate maintains an acceptable subset of stops and ranks the accepted ones by current desirability, both explicitly live and expected to drift over a search more than most priorities do.

**Tractability check.** Some career-phase stops — a pure-paycheck stop specifically — deliberately disclaim any occupation or industry relevance, which means they also remove the one axis that would otherwise implicitly bound a search. If the acceptable subset includes a stop like this, the elicitation layer confirms that at least one other priority carries a mandatory flag or a sufficiently tight threshold (a geographic target, a schedule constraint, an employer-type restriction) before evidence-gathering runs. If none does, that's not a silent failure and not a silently unbounded search — it's itself a new decision node ("what's actually bounding this for you?") surfaced back to the candidate, the same way any other unresolved structural question is.

**Qualification.** Distinct from a priority: not a candidate preference, but a candidate's own attested fact compared against a listing's stated requirement. Mechanically this reuses the threshold/mandatory math rather than adding a new mechanism, just with the roles reversed — for a priority, the candidate's preference supplies the cutoff and the listing supplies the measured value (a salary floor vs. an attested salary); for a qualification, the listing's stated requirement supplies the cutoff and the candidate's own attested fact supplies the measured value (a required license vs. whether the candidate holds one; a minimum years-of-experience vs. the candidate's actual years). A boolean qualification (a license, a clearance) behaves like mandatory; a graded qualification with a floor (years of experience, degree level) behaves like threshold. This maps directly onto how real postings already distinguish minimum from desired qualifications: an unmet minimum qualification is controlling (the listing is excluded regardless of fit elsewhere); an unmet desired qualification is non-controlling, a soft signal rather than a disqualifier.

**Aptitude.** Also distinct from a priority: not what the candidate wants, and not a qualification check, but the candidate's own trait strength — nonpolar, meaning each aptitude is an independent ordinal rating (not a strong trait / about average / above average / exceptional), not a bipolar trade-off the way a polarity-shaped priority is. Being strong at solo work says nothing about being weak at group work; a polarity says something did trade off, an aptitude doesn't assume that. Aptitude feeds a second, separate fit score per listing — the candidate's own strength on a trait compared against how much a listing (or its occupation) demands that trait — kept alongside the priority-based preference fit, never blended into it. The demand side of that comparison doesn't need new data collection: O*NET's Work Styles domain already publishes, per occupation, importance ratings for traits like attention to detail, stress tolerance, independence, and cooperation, collected from real job incumbents and freely available. The candidate side starts as optional and self-report only — a real timed instrument (O*NET's Ability Profiler covers a different, narrower set of cognitive/psychomotor abilities via an actual test rather than self-report) is a plausible future mux, not something to build now, and would need its license terms verified before ever being administered inside the tool.

**Dimension**, generalized. A dimension is a named grouping of search/ranking modifiers, not only a grouping of preference priorities. Three kinds exist so far, sharing the umbrella but not the mechanics: a **preference dimension** (work style, lifestyle, compensation) groups priorities that the candidate ranks against each other by pairwise tournament, and the dimension itself is ranked against other dimensions using the same tournament-plus-Bradley-Terry mechanism — the same mechanism reused at a coarser grain, not a second one. A priority's final weight is its dimension's rank multiplied by its rank within that dimension. An **aptitude dimension** is weighted differently in kind, not just in degree: nothing about it is candidate-ranked, since a candidate doesn't meaningfully "prefer" one aptitude over another the way they prefer compensation over lifestyle — the weighting comes from how important a trait is to the specific job or occupation, using the same O*NET Work Styles data that supplies the demand side of the aptitude-fit comparison. A **qualification dimension** isn't ranked or weighted at all in the preference sense — it's evaluated as met, unmet, or a percentage of desired qualifications met, driven by the listing's own minimum-vs-desired framing. Each dimension kind produces its own labeled fit sub-score; these don't collapse into one number by default. The plan stage synthesizes across them, consistent with the standing discipline that scoring stays mechanical while judgment stays in the plan stage. (A single blended score across all of this is a legitimate alternative someone could choose instead — ai-job-search's own rubric folds skill-match, experience, culture, and career alignment into one weighted average — but JobMux's design keeps them separate on the bet that a candidate is better served seeing why a listing scored where it did than seeing one number.)

Marking a priority, a qualification, or an entire dimension **not critical** removes it from scoring entirely — a weight-zeroing event handled by the reallocation rule below, not a separate mechanism.

Every priority is scored against one of four evidence kinds gathered by the evidence-gathering layer: **attested attributes** (hard, listing-checkable facts — full-time/part-time, on-site/hybrid, salary), **inferable attributes** (soft job-character qualities — variety, autonomy, pace — inferred from a posting's own words, only with a quoted basis, never a bare guess), **reference-data lookups** (a value pulled from a trusted external dataset keyed by a listing attribute, rather than extracted from the listing's text or inferred with a quoted basis — a location's cost-of-living index, used to normalize compensation, is the running case; see §1.2), and **analog-sourced signals** (evidence obtained through direct human contact — a phone call, a direct contact, a private distribution list — rather than any digital extraction, inference, or lookup; see AnalogSearch, §1.2).

**Live, mutable state.** A priority's threshold or mandatory flag, and its rank, are live state, independently revisable by the candidate at any point — not a one-time handoff to the later stages. Either can be added, tightened, loosened, or removed without affecting the other: a scalar's threshold can loosen or tighten continuously along its existing scale (a geographic radius, a salary floor, an hours-per-week floor); a target's mandatory flag is closer to a binary add/remove, since there's no partial credit for an inexact match once it's set. The same applies to a dimension's rank relative to other dimensions, and to career phase's (or any category filter's) acceptable subset and ranking. **Only the candidate originates a change** — the same discipline as the original interview ("confirmation counts; the brief said so does not") extends to updates: the system may report that a constraint is producing thin or zero results, exactly as the search stage reports "none found," but it never loosens, tightens, adds, drops, or reweights anything on its own initiative.

**Reallocation rule for priority reweighting.** When a candidate adjusts one priority's rank, the remaining budget within its dimension redistributes across the others in proportion to their current relative shares (new weight = old weight ÷ sum-of-others × remaining budget) — the default, because it doesn't silently reorder priorities the candidate didn't touch. The same rule applies one level up when a dimension's rank changes relative to other dimensions. Two alternatives stay available rather than assumed-default: equal-split redistribution (simpler, flattens relative conviction), and protect-top-K (lock the top priority or dimension, let only lower-ranked ones absorb the change) — useful when one preference is near-non-negotiable without having been marked mandatory or given a threshold.

**Every change produces two outputs:** a cheap refilter/rescore against evidence already on hand, done immediately in-conversation; and an optional strategy-reassessment suggestion, surfaced but never acted on unasked, since a change to a priority's threshold or mandatory flag (especially loosening or removing one) can flip which evidence-gathering module even applies — e.g. a geographic target's mandatory flag being removed likely means the adaptive module (§1.2) is no longer the right primary tool, and board-heuristic/board-ML scanning becomes the better fit.

**Scoring function for ranked priorities.** A plain weighted sum (Σ weight × score per priority) lets a strong score on one priority compensate for a terrible score on a highly-ranked one. Mandatory targets and unmet thresholds already act as hard cutoffs regardless (that's what makes a priority controlling), so top-ranked priorities use a softer version of the same logic among themselves — penalizing the worst-scoring highly-ranked priority disproportionately (Chebyshev-style) rather than pure linear weighting, so a candidate's #1 priority can't be fully cancelled out by a strong #3.

This deterministic approach is a deliberate choice, not a default reached for lack of imagination — worth stating plainly since it's a real fork in the road among existing prior art. career-ops explicitly rejects fixed weights in favor of pure LLM holistic judgment, on the stated grounds that a closed-form formula would "over-fit" the heterogeneity of real job contexts, and accepts that "two different LLMs may produce slightly different scores on the same input." That argument conflates two different things: whether math is involved at all (it always is — an LLM's inference is math too, just not in inspectable form) and whether the weighting step specifically is explicit and reproducible or opaque and potentially inconsistent across runs. ai-job-search's own evaluation rubric is a concrete counter-example sitting in the same problem space: fixed, published percentage weights (technical skills 30%, experience match 25%, behavioral fit 15%, career alignment 30%) that work fine and are fully auditable. JobMux's bet follows ai-job-search's shape, not career-ops's: when a deterministic formula doesn't capture something real, that's a signal to refine the formula's inputs or shape, not a reason to move the weighting into a black box. This doesn't mean every step is closed-form — §2.3's frontier tier exists precisely for the parts that genuinely need contextual judgment. The discipline is knowing that aggregating already-extracted values into a score isn't one of those parts.

**Conversational realization.** Since this runs as a Skill/conversation, constraint edits aren't literal widgets: a candidate says "bump up compensation" or "forget the Mankato thing, anywhere in Minnesota now," the system does the reallocation or refilter math, and reflects the new state back for confirmation before rescoring ("compensation now 35% (was 20%); geography is no longer mandatory — 41 previously-excluded listings now qualify, want to see them?").

### 1.2 Evidence-gathering layer

Downstream of the elicitation layer, parameterized by what it produced. **Modular, not a single fixed methodology** — what counts as the right way to search depends on what stage 1 surfaced:

- A candidate whose dominant decision node is a geographic anchor into a sector with small, scattered employers needs the **adaptive discovery module**: employer-directory-first rather than keyword-first, checking trade/professional associations directly for private job-distribution channels smaller members rely on instead of their own sites, scanning larger employers' boards broadly by department rather than narrowly by title keyword, treating discovery and monitoring as genuinely different problems. This is the reference implementation (concept brief case 1).
- **Board-heuristic module.** Common job boards and ATS platforms, queried with a fixed, defined set of search terms and criteria decided in advance — algorithmic tier (§2.3): no model judgment decides what counts as a match, the criteria are applied mechanically. This is not an alternative offered only to candidates who don't need the rest of JobMux — it's a necessary component of nearly every case strategy, since even an adaptive search should sweep the well-indexed subset of its market before spending effort on the part that isn't. A candidate whose dominant decision nodes are closer to "open to relocation, industry-agnostic, needs a compensation floor met" (concept brief case 3) may need little beyond this module; other cases layer the remaining modules on top of it, not instead of it. JobSpy (speedyapply) is directly reusable here rather than a pattern to re-derive — a maintained Python library that already scrapes LinkedIn, Indeed, Glassdoor, Google Jobs, and ZipRecruiter concurrently into one schema. freehire (strelov1) and jobseek (colophon-group) are further reference implementations of the same fetch → normalize → dedup → upsert shape at larger scale, worth studying for their per-ATS source-adapter pattern even though both are scoped to IT/tech roles and so aren't themselves usable as a data source outside that sector.
- **Board-ML module.** The same job boards and ATS platforms, but with an LLM in the loop judging which results are truly relevant and deriving new or refined search terms/tactics/strategies as it goes — frontier tier (§2.3): genuine adaptive judgment, not a fixed rule applied mechanically, which is what distinguishes it from the board-heuristic module above rather than any difference in which boards get searched. Digging out useful terms via a search engine's own query-similarity features (e.g. Indeed's "People also searched," which is how the original source project grew its title list outward) is the cheapest version of this behavior, worth trying before a full frontier-tier pass. Board-heuristic is the right cheap-first-pass default (§1.5); escalate to board-ML when the heuristic pass's results are ambiguous enough that judging true relevance, or growing the term list further, needs real judgment.
- A candidate whose dominant decision node is values/mission-alignment needs a module closer to employer research against stated values than listing discovery (concept brief case 2).
- **Signal-fusion module** (concept brief case 4): for opportunities where a digital trace exists but is a weak or misleading proxy for real availability (a stale-but-rendering listing, an evergreen "always hiring" posting), the module holds the digital trace and any analog lead (see AnalogSearch, below) as signals in an open, tagged evidence set (§1.4) and reconciles them into a single confidence-rated status, rather than accepting whichever arrived first. See §1.3 for how this extends the verification layer's core rule to analog leads, and §1.4 for the general reconciliation mechanism this module instantiates.

**AnalogSearch.** A named technique, not a module of its own — actively pursuing human/relational channels (a phone call, a direct contact, a private association list or distribution channel) rather than a digital query. It serves two of the uses above: on the discovery side, it's how gatekeeper/network discovery (below) actually reaches an opportunity with no digital footprint at all; on the verification side, it's how the signal-fusion module obtains the analog lead it reconciles against a digital trace. Either use produces the fourth evidence kind defined in §1.1 — an analog-sourced signal, gathered through direct human contact rather than any digital extraction, inference, or lookup. Whether AnalogSearch is worth running at all is already governed by the same conditions that gate the adaptive module and the signal-fusion module — it doesn't need its own decision node.

**Compensation normalization.** A candidate's compensation priority (typically a scalar with a floor) is stated in the currency the candidate actually intends to spend it in, not an abstract index. The right normalization anchor is downstream of how the geography decision node resolved, not an independent choice: a fixed-destination resolution means every listing's attested salary gets converted into destination-equivalent terms before comparison, regardless of where the job itself is physically located, since that's the one place the candidate's real budget lives; an open or floating geography resolution means there's no single destination to anchor to, so the anchor instead needs to be a location-agnostic reference index (a standard national-average cost-of-living index) or the candidate's current location. The conversion itself — a listing's salary multiplied by the ratio of the anchor's cost-of-living index to the listing location's — is pure arithmetic once both index values are known (§2.3). Fetching a location's index value is a reference-data lookup: pulled from a trusted external dataset keyed by a listing attribute, rather than extracted from the listing's text or inferred with a quoted basis.

Three disciplines are structural and carry into every module:

- **Template-instantiation over free synthesis** — the method, the forbiddens, and the output shape are fixed, human-reviewed text that gets slot-filled per run, never regenerated or "improved" by the model on the fly. This is what stops rules from drifting or getting forgotten run to run.
- **Evidence, not advice** — the search stage reports what it found, including "none found," and is forbidden from scoring or ranking how well a result fits the candidate; that judgment belongs to the plan stage.
- **No irreversible actions** — the system never submits an application, contacts an employer, or joins a private channel on the candidate's behalf. It drafts and recommends; the candidate always executes. (career-ops already earns this distinction as a filter, not an auto-applier; AIHawk doesn't, which is a large part of why it reads as spray-and-pray rather than a tool worth trusting with judgment calls.)

**Gatekeeper/network discovery is its own explicit sub-step**, distinct from and logically prior to "check the association's private channel." The hard part in a fragmented, relational market usually isn't networking with a contact you already have — it's discovering which network or gatekeeper is even the relevant one before any relationship-building can start. Confirming that a given trade association, not a similarly-named one, is the authoritative body for a sector, and that it runs a given private distribution channel, is itself a multi-step search problem, and typically requires AnalogSearch to close out once the right gatekeeper is identified. A module that jumps straight to "check the obvious trade association" will miss sectors where the obvious-looking body is wrong, defunct, or actively unsafe to use without verification (a compromised page on an otherwise-genuine organization's site is a real, observed failure mode, not a hypothetical one). This sub-step is the hardest test case for the roadmap's analog-only cases (concept brief §4.2) — union-hall jurisdiction identification in particular.

**Persistence is not one gate but three, and they're easy to conflate.** A result that doesn't currently clear the threshold to *display* to the candidate isn't automatically a result that should never be *persisted* — and a result that should never be persisted isn't automatically the same kind of "doesn't fit" as one that's merely a near-miss. Three distinct cases:

- **Near-miss.** A real, legitimate candidate for this search that fails a specific, nameable threshold, mandatory flag, or qualification by a knowable amount. Stays tagged with which constraint it failed and by how much. Without this, a later constraint change (a threshold loosening, tightening, being added, or being removed) can't cheaply resurrect a previously-filtered listing from cache and has to re-run a full search instead. (`jobmux/verification.py`'s `NearMiss`/`refilter_near_misses` implements exactly this.)
- **False positive / category error.** Not a legitimate candidate at all — a title or keyword collision that puts the result in a different occupation entirely (a hospital's "Environmental Services" posting surfacing under an environmental-science search is the canonical case). This is never persisted as a near-miss, or as data about that listing at all. Instead it corrects the search itself: a confirmed false-positive pattern is recorded in a small, permanent exclusion registry, checked at persistence time, applied retroactively to purge anything already in the cache matching the pattern and prospectively to keep it from being re-surfaced. This is a correction to the search vocabulary, not a fact about one listing's fit. `jobmux/verification.py` has a reference implementation; §2.3 covers why matching against an already-confirmed pattern is algorithmic-tier even though *confirming* that a given result actually is a false positive (as opposed to a genuine, if unusual, near-miss) is frontier-tier judgment.
- **Domain-gap from a structural priority shift.** A career-phase (or other category-filter) change wide enough to open a genuinely different search domain — e.g. career phase admitting "it's a paycheck" jobs with no tie to the candidate's field at all — isn't served by refiltering either cache above, since nothing in them was ever gathered under those terms. This routes to the repeat-search half of §1.1's "every change produces two outputs" rule, not the cheap-refilter half.

Only the first two are genuinely about a single listing's persistence; the third is a signal that the *search itself* needs to run again, not that anything already gathered needs re-evaluating.

### 1.3 Verification/trust layer

Whichever evidence-gathering module runs, results need to be trustworthy before they reach the plan stage:

- A signal can motivate a check. It can never *be* the check — treat anything not directly loaded/confirmed as a signal, not a finding. This cuts both ways: things that look newly gone need the same scrutiny as things that look newly available. **This now covers analog leads, not just digital search-tool output** — a phone tip or a rumor that a role is reopening is a signal requiring the same confirmation discipline as a search result (concept brief case 4).
- **Escalation ladder for a source that comes up empty on a first guess:** re-derive from the source's own structure before re-guessing blindly; try a targeted site-scoped search; check a trusted third-party or association directory for that category; if still unresolved, mark it distinctly as "unable to verify" — never silently as a confirmed negative.
- Platform-specific gotchas are worth cataloguing as they're discovered — e.g. one common government-jobs platform keeps listing pages rendering normally for months after the closing date with no "expired" indicator; always read the date field, don't trust that a page loading means it's current. (This particular gotcha is the seed case for the signal-fusion module, §1.2. It's also a known problem elsewhere — career-ops's own liveness checker has needed repeated regex tightening after false positives on multi-month-old jobs, which is independent confirmation this is a recurring class of bug, not a one-off.)

### 1.4 Recombination / tracking layer

Where the plan stage and an ongoing tracker come together — the fit judgment happens here, mapping the candidate's priorities, career phase and other category filters, qualifications, and aptitudes against the evidence-gathering layer's attested, inferred, reference-data, and analog-sourced attribute tags, never earlier. The tracking schema: per-opportunity a career-phase tag and a separate tag for whatever discovery context surfaced it (which module, which geographic or search tier, and so on) — kept as distinct fields rather than folded into one general "category" column, since collapsing two different axes into a single field risks exactly the kind of ambiguity a fixed vocabulary exists to prevent — plus status, prior status (for change history), a stable ID where available, source, first-seen/last-checked dates, a confidence label and a numeric confidence value for how the status was verified (see below), a volatility tier for scheduling re-checks (a scheduling tool, not a stability guarantee — verify periodically regardless), and free-text notes. Status changes are revised in place with visible prior-value history, never silently deleted.

**Evidence-signal model (decided).** Rather than a fixed pair of channels (one "digital" signal vs. one "analog" signal), the tracking schema holds an open, variable-length list of tagged evidence signals per opportunity: `(source, state, timestamp or quoted basis)`. `source` names which evidence-gathering module or technique produced the signal — board-heuristic, board-ML, adaptive, or analog (§1.2) — where an analog signal may be system-orchestrated (AnalogSearch) or candidate-volunteered (a candidate directly reporting a lead, e.g. "a friend told me there's an opening," is just another analog-tagged signal, not a special case requiring its own mechanism). `state` is per-signal: confirmed, contradicted, pending (identified and drafted but not yet executed — see the signal-fusion module's Analog-pending outcome), or unable-to-obtain. Judging what state an individual signal deserves — how reliable this particular source is, how recent the underlying event actually is, how specific it is to this listing rather than the employer in general — is frontier-tier judgment (§2.3) and is not delegated down.

Reconciliation is a separate, later step, run once every signal in the set already carries its own state: characterize the set as concordant (agreeing confirmed signals) or discordant (disagreeing confirmed signals), then derive two things from that characterization — a human-readable **outcome label** (the signal-fusion module's Concordant confirmation, Analog-resolved, Digital-only, Analog-pending, Conflicting, and Unable-to-verify outcomes, §3 of that file, are now understood as derived labels for particular shapes of the general signal set, not six hardcoded two-channel cases) and a **numeric confidence value**. Both are algorithmic-tier (§2.3) once the input states are known — deriving a label or a number from an already-characterized set is mechanical, even though characterizing any one signal's own state was not. The numeric confidence value is kept separate from priority-based fit-scoring (§1.1) — confidence about whether a listing is real has no business affecting how well it matches what the candidate wants — but is a real input to §1.5's information-gain-per-cost ordering: low confidence on a listing the candidate cares about is exactly the kind of high-expected-gain action that ordering should surface. The exact derivation formula for the numeric value is not settled by this decision — flagged as a first-instantiation question the same way `jobmux/scoring.py`'s Chebyshev formula is (see that module's docstring), not a closed decision.

This resolves the confidence-label vocabulary question `reference/adaptive-module.md` §10, `reference/signal-fusion-module.md` §3/§7, and `reference/verification-escalation-policy.md` §7 each independently flagged as open and deferred to this layer. The persistence-gate taxonomy (near-miss / false positive / domain-gap) that determines what even enters this tracking schema in the first place is covered in §1.2, not repeated here.

One disposition carried forward specifically: a **"watch, don't act yet"** tag, separate from the career-phase and discovery-context tags, for real opportunities that aren't a fit today — split into **growth-track** (a genuine fit for a more experienced future version of the candidate) and **stretch-pitch** (not a clean match on paper today, but worth a direct, honest case for transferable strengths, especially if the opportunity stays open longer than typical — itself a signal worth acting on).

**Recheck cadence should be funding/cycle-aware, not just calendar-based.** Many small-employer or grant-funded opportunities post and hire on an external clock (a grant renewal, a levy passing, a fiscal-year open, an apprenticeship intake window) rather than at random — "check back weekly" is the wrong habit for these; knowing the funding or enrollment calendar matters more than refreshing a board on a fixed interval. This is a first-class input to the volatility-tier scheduling above, not a separate mechanism.

### 1.5 Dynamic prioritization and cost-aware strategy selection

**A separate cost/budget axis, not part of the same weight vector as the preference sliders.** The preference sliders (geography, compensation, career phase, etc.) are weights over outcomes; cost is a constraint on the process — how much effort is spent discovering and verifying — and belongs in its own value-of-information calculation. Concretely: order candidate actions (run a given module, escalate to the next rung of §1.3's verification ladder, broaden a filter) by expected information gain divided by cost, and spend the budget on the best ratios first. §1.4's numeric confidence value is a natural input to this ordering's expected-information-gain term: low confidence on an otherwise high-priority listing represents high remaining expected gain, and near-maximal confidence represents near-zero gain regardless of budget. "Cost is not an object" isn't a separate mode — it's the same ordering with the budget parameter set arbitrarily high, which naturally reduces to running every action with positive expected value. One boundary stays fixed regardless of budget: cost-awareness governs how much gets searched and how many strategies get tried, never the rigor applied to confirming any one finding — §1.3's "a signal is a signal, not a finding" standard isn't for sale at any budget level. §1.3's own rule for a genuinely tight budget ("verify fewer rows completely, don't verify more rows partially") is already a value-of-information statement, not a separate rule — a fully-confirmed row is worth more than two half-confirmed ones. §2.2's model-tiering (cheap model for mechanical extraction, higher-effort model reserved for judgment) is compute-cost-awareness; §1.3's anti-corner-cutting clause is human-effort-cost-awareness — the same idea, two resources.

Studying career-ops's and AIHawk's actual open-source implementations (URL/page-pattern detection for Greenhouse/Ashby/Lever, career-ops's Playwright-based navigation, its evaluation rubric) is the right first move for the cheap first rung of this cost-aware ladder, rather than re-implementing ATS detection and navigation from first principles — re-deriving a solved problem is exactly the low-value-per-cost spend this section's own ordering logic argues against. JobSpy (speedyapply, pip-installable) goes a step further than "study" — it's a maintained library covering LinkedIn/Indeed/Glassdoor/Google/ZipRecruiter concurrently and is a plausible direct dependency for this rung rather than code to rewrite. freehire (strelov1) and jobseek (colophon-group) are worth a design-level look rather than reuse: both structure their per-ATS crawling behind a small adapter interface (one adapter per platform, one config line per company), which is the right shape for this module's own source list to grow without touching its core logic. jobseek's company-onboarding workflow is also worth borrowing directly: a CLI tool designed to be driven by a coding agent rather than a human, walking it through finding a requested employer's career page, selecting the right adapter, and validating the result — a pattern that maps cleanly onto the adaptive module's own "add a newly-discovered small employer to the watch list" problem (§1.2).

**A hard floor, not just a soft budget.** The information-gain-per-cost ordering above is continuous — cost pressure changes what gets tried, but doesn't change what's allowed. A candidate can also set a hard preference — minimize frontier-model inference — which forces every task down to the algorithmic or small-model tier (§2.3) wherever that's possible at all, and permits frontier-tier calls only for the handful of tasks §2.3 already marks as unsafe to delegate down (the interview itself, gatekeeper judgment calls, escalation-ladder calls, digital/analog signal reconciliation). This is a mode switch on the existing ordering, not a new mechanism — the same non-negotiable floor from §2.3 (never downgrade a task that genuinely needs judgment, regardless of budget) applies whichever mode is active.

### 1.6 Standards adopted

Where an external standard already exists for a piece of vocabulary, JobMux adopts it rather than inventing an equivalent — written in plain spaced form in reference docs, with the exact external token noted for implementation. Occupation aligns with the Standard Occupational Classification (SOC); industry aligns with the North American Industry Classification System (NAICS); employment type, base compensation, closing/staleness dates, and experience/education requirements align with schema.org's `JobPosting` properties (`employmentType`, `baseSalary`, `validThrough`, `experienceRequirements`, `educationRequirements`); the demand side of an aptitude comparison aligns with O*NET's Work Styles importance ratings, published per occupation and free to use. Extending beyond an adopted standard is warranted only once something concrete earns its keep (§2.1's same discipline, applied to vocabulary rather than packaging) — work schedule (shift timing) is the one category filter identified so far with no equivalent existing standard, and is JobMux's own vocabulary by necessity, not by default. This is also a checked claim, not an aspiration: none of career-ops, ai-job-search, AIHawk, freehire, JobSpy, or jobseek ground their own occupation, industry, or skill vocabulary in an external standard — career-ops's "archetype" taxonomy is bespoke and specific to AI/tech roles; ai-job-search uses arbitrary 0–100 scales; AIHawk's config uses real geographic region codes for location but nothing equivalent for occupation or skills; freehire and jobseek both derive region/seniority/skill facets from their own curated dictionaries; JobSpy's `JobPost` schema is a flat, atomistic shape with per-board bonus fields (LinkedIn's `job_level`, Naukri's `skills`) rather than anything grounded in SOC, NAICS, or schema.org.

## 2. Format & infrastructure

### 2.1 Packaging format (decided)

Build as a **Claude Skill** (SKILL.md + reference docs/templates) — direct precedent in career-ops and Proficiently, immediately usable in Cowork/Claude Code. Reference docs in plain markdown, not skill-specific syntax, so they can be lifted into a tool-agnostic repo later. The `skill-creator` skill handles the packaging step once content is drafted. The "template-instantiation over free synthesis" pattern (§1.2) applies reflexively to the Skill's own construction: the core rules (interview forbiddens, search-stage forbiddens, verification ladder) should live as fixed reference text the model follows verbatim, not guidance it reconstructs from a description each run.

### 2.2 Execution infrastructure (open)

A single Skill only runs inside an interactive session — a human has to be present to say "go," and every check happens serially inside one chat turn, consuming that session's context and running everything at one model tier throughout. That's a real fit for §1.1 (the elicitation interview genuinely wants a live conversational partner, and probably always will) but a real limitation for §1.2–§1.4 in two ways:

- *Autonomy:* the volatility-weighted recheck cadence, the turnover-signal behind the stretch-pitch disposition, and any bulk multi-employer sweep all want to run on a schedule and report back only when something changed, not wait for a human to reopen a session.
- *Efficiency:* most of what the verification layer needs per listing — read a date field, extract a few structured attributes, flag staleness — is narrow and mechanical. Running it at the same model tier as the elicitation interview and plan-writing judgment calls is real waste; a cheap/fast model does the extraction for a fraction of the cost and latency.

Three options, increasing infrastructure investment:

1. **Single Skill, one model.** No tiering, no autonomy — a human drives every pass. Fine for a single, occasional, elicitation-heavy search; doesn't scale past one attentive user.
2. **A suite of Skills with subagent-based tiering**, still inside Cowork/Claude Code, no custom infrastructure. If §1's layers become separate Skills, the orchestrating instructions can spawn subagents with a specified model for bounded sub-tasks — a fast/cheap tier for bulk per-employer extraction, the higher-effort tier reserved for the orchestrating thread's interview and judgment work. Subagents start cold with no shared context, so batch sensibly (one per employer or batch of listings, not one per field) for this to pay off. Each subagent call receives a fixed, defined **context pack** — a single canonical object per session revision, computed as a fold over the §2.4 event log and regenerated whenever that fold changes (any priority, threshold, mandatory-flag, rank, or category-filter edit — never on a fixed timer). A subagent's task template pulls only the named sections its task needs and reuses them verbatim, rather than re-deriving its own framing of what matters. This is the same template-drift risk §2.1 already guards against at the Skill level, recurring one level down at the subagent-prompt level; the fix is the same discipline, just applied again.

**Context-pack contract (decided):**

```json
{
  "pack_id": "<hash>",
  "session_id": "...",
  "folded_from_event_seq": 1842,
  "generated_at": "...",

  "active_priorities": [
    {
      "name": "commute_tolerance",
      "dimension": "lifestyle",
      "shape": "scalar",
      "threshold": {"value": 60, "unit": "miles"},
      "mandatory": false,
      "not_critical": false,
      "weight": 0.18
    }
  ],

  "category_filters": [
    {
      "name": "career_phase",
      "acceptable_set": ["optimal_local", "optimal_with_travel", "field_adjacent"],
      "ranking": ["optimal_local", "optimal_with_travel", "field_adjacent"]
    }
  ],

  "qualifications": [
    {"name": "environmental_science_degree", "type": "mandatory"},
    {"name": "years_experience", "type": "threshold", "floor": 0}
  ],

  "aptitudes_requested": [],

  "attested_schema": ["employmentType", "baseSalary", "jobLocation", "validThrough"],
  "inferable_schema": [],

  "reference_anchors": {
    "compensation_normalization": {
      "mode": "fixed_destination",
      "anchor_location": "Mankato, MN"
    }
  },

  "discovery_context": {
    "active_modules": ["adaptive", "board_heuristic"]
  },

  "near_miss_vocabulary": {
    "failure_reasons": ["threshold:<priority_name>", "mandatory:target_missed", "qualification:unmet_minimum"]
  },

  "forbidden_scope": "<verbatim template-instantiated text: extract/tag only, no scoring, no ranking, 'none found' is a valid result>"
}
```

The shape enforces two disciplines structurally rather than by instruction alone: `inferable_schema` stays empty for any subagent restricted to the small-model tier, since inferable-attribute tagging requires a quoted basis and is frontier-tier only (§2.3) — a pack built for a small-model call can't hand it a task it isn't allowed to attempt. And `active_priorities`/`attested_schema` are pre-filtered to what's currently live and not flagged not-critical, so a subagent never spends extraction effort on a dimension nobody's scoring against — §1.5's cost-awareness applied as pack-trimming, not a separate mechanism. `weight` is carried for debugging visibility only; no subagent computes with it, since weighted scoring is algorithmic and stays in the orchestrator (§2.3).
3. **A custom API-driven backend** — the Messages API's Tool Runner or Managed Agents, backed by real persistent storage instead of a spreadsheet a human edits by hand. Delivers true autonomous scheduling, not just cheaper tiering, and the finest-grained control over which model handles which call. Highest build cost.

A lower-effort middle ground on autonomy specifically, worth trying before option 3: Cowork's scheduled-tasks primitive can already trigger a Skill to run on a cadence, which may cover the autonomy half even while staying on option 1 or 2 for tiering.

**Current conclusion: option 2 covers what's currently envisioned, without writing a custom backend.** Persistence (§2.4) doesn't require option 3 either — flat files already work, and the source project's own ledger is a working proof of that. The two gaps option 1 leaves on its own — autonomy and model-tiering — both already have answers inside Cowork/Claude Code without custom infrastructure: Cowork's scheduled-tasks primitive covers autonomous recheck cadence, and the Agent tool's model override covers tiering via subagents. So the fastest path to something useful is option 2, not option 1 alone and not option 3 — with the honest trade-off that it's Cowork/Claude-Code-native rather than a portable standalone product from day one. That's consistent with writing reference docs in plain markdown (§2.1): start Cowork-native and cheap, generalize to other platforms or a fuller custom UI later, once the design has proven out. Design the elicitation layer to work identically regardless; treat the infrastructure choice as a property of the evidence-gathering/tracking layers only.

### 2.3 Algorithmic vs. small-model vs. frontier-tier tasks

A rough test for sorting any given task: does it require holding conversational context and forming a judgment someone could reasonably contest, does it require reading unstructured prose to extract or classify a single bounded fact, or is it pure arithmetic/lookup once the inputs are already known?

**Algorithmic — no model call needed:** the §1.1 proportional-reallocation formula; converting tournament win-counts into Bradley-Terry cardinal ranks; the weighted-sum/Chebyshev scoring formula; ordering candidate actions by information-gain-per-cost; volatility-tier recheck-cadence scheduling; diffing an old ledger value against a new one to decide what gets flagged as changed; re-filtering the near-miss evidence cache against a changed threshold, mandatory flag, or qualification; matching a listing against an already-confirmed false-positive exclusion pattern (§1.2); running the board-heuristic module's fixed-criteria board query (§1.2); characterizing an evidence-signal set (§1.4) as concordant or discordant once each signal's own state is already known, and deriving both a human-readable outcome label and a numeric confidence value from that characterization; comparing a page's stated closing date against today's date once the date field is located; converting a listing's attested salary to anchor-equivalent terms via a cost-of-living index ratio, once both index values are known (§1.2); computing a qualification dimension's met/unmet percentage once each qualification has been checked; generating a session's §2.2 context pack via a fold over the event log, sliced to live, not-critical-excluded priorities and their relevant attribute schema. This tier is implemented as literal deterministic code run via the execution sandbox, never as a model call asked to perform arithmetic or lookup — that's what keeps the tier distinction real rather than aspirational, and what keeps rescoring genuinely cheap even as the evidence cache grows across a multi-year candidate relationship (§2.4).

**Small/cheap-model-plausible:** pulling attested attributes (salary, hours, on-site/hybrid, location) out of a job posting's free text; classifying whether a fetched page is a client-rendered shell or an actual result; recognizing which ATS platform a URL or page structure belongs to; tagging which specific threshold, mandatory flag, or qualification a near-miss failed and by roughly how much; resolving an ambiguous location string to the reference-dataset key a cost-of-living lookup needs; extracting a schema.org `JobPosting` block from a page's structured data when present, before falling back to prose extraction.

Model choice for this tier is decided, not left abstract: given §2.2's Cowork/Claude-Code-native infrastructure, tiering runs through the Agent tool's model override, whose small-model option is **Claude Haiku 4.5** (`claude-haiku-4-5-20251001`) — every task listed above is scoped to that model. A different small model only enters consideration if the project pursues the README's stated extension beyond Cowork/Claude Code (§2.1), and isn't worth designing for before that happens.

**Frontier-tier — can't be safely delegated down:** the interview itself (holding revisable hypotheses about a candidate's decision nodes, testing them against the candidate's actual words, judging resolved-vs-genuinely-open); inferable-attribute tagging that requires a quoted basis rather than a bare guess; the plan stage's fit judgment, including treating a genuine tension or cycle as a real finding rather than noise to resolve away; gatekeeper/network discovery (judging which body is authoritative, catching a compromised page on an otherwise-genuine site); escalation-ladder judgment calls (distinguishing a wrong URL guess from a genuinely gone listing); the board-ML module's relevance judgment and search-term/tactic refinement (§1.2); confirming that a given result actually is a false positive rather than a genuine near-miss (§1.2); judging an individual evidence signal's own state — reliability, recency of the underlying event, specificity to this listing — in the signal-fusion module (§1.4); and any "does this threshold, mandatory flag, qualification, or career-phase change flip which search module applies" reasoning.

Budget pressure can justify running more of the algorithmic and small-model tier and less of everything else, but never justifies quietly downgrading a frontier-tier task to a cheaper model to save money — the same corner-cutting §1.3 already forbids for time, showing up again for compute spend.

### 2.4 Persistence layer

§1.1's live weight vector, mutable threshold/mandatory/qualification settings, career-phase (and other category filter) acceptable-set-and-ranking, and near-miss-tagged evidence cache all need to survive between sessions — a candidate revising a constraint weeks later has to have that revision apply against evidence already gathered, which can't live only inside one chat session's context.

Three options, mirroring §2.2's structure:

1. **Flat structured files** — a JSON/YAML file for the live weight/threshold state and its revision history, a spreadsheet for the tracking ledger (what the source project already does successfully). Simplest, human-readable, no new technology, works under any of §2.2's three infrastructure tiers.
2. **A lightweight embedded database (e.g. SQLite)** — earns its keep once the near-miss evidence cache grows large enough that querying it ("show me everything rejected only on a specific threshold") matters more than reading a file.
3. **A pluggable storage interface** — abstract state reads/writes behind a small defined interface (get_state / set_state / query_evidence(filter)) so the backend underneath can be swapped without touching the rest of the architecture.

**Decided approach:** start with option 1's backend, structured as an append-only event log rather than a mutable-current-state file with history bolted on afterward — each change to a priority's threshold, mandatory flag, or rank, a qualification's value, a dimension's rank, or a category filter's acceptable set or ranking is recorded as an immutable event, and current state is computed as a fold over that log. This is a stronger version of §1.1's "nothing gets overwritten" commitment: it's structurally impossible to lose a prior value, not just a stated intention. It also makes a later move to option 2 nearly free, since an event log maps directly onto a table, where a mutable-state-plus-annotations file would need real restructuring to migrate. Access is still written through option 3's thin interface from the start, so the backend can change without touching the rest of the architecture — the same discipline §1.2 already applies to evidence-gathering, treated here as a property of persistence.

Any sensitive, candidate-specific session-level content (a real transcript of a call made during AnalogSearch, for instance) should follow a pattern already proven elsewhere rather than invent one: career-ops keeps its own per-session interview transcripts in a gitignored directory with only a README and a placeholder tracked, so real names and company-specific content never enter version control. The same convention — track the schema and documentation, never the sensitive instance data — applies directly to any analogous JobMux session content.
